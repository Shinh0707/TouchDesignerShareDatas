    開発ガイド¶

    全体像¶

    CHOP/<Name>/            TOP/<Category>/<Name>/       ← 1 フォルダ = 1 プラグイン(src/ があれば自動で認識)
  includes/  src/  tests/  plugin.cmake(任意)
TDLib/                  TouchDesigner SDK ヘッダ
testing/tdmock/         TD を起動せずにプラグインを読み込んで cook する「モックホスト」
testing/host/           全プラグイン共通の smoke テスト / パラメータ情報の書き出し
cmake/TDPlugin.cmake    自動検出とターゲット生成
tools/                  new_plugin.py / gen_docs.py / package.py
docs/                   このサイト(plugins/*.md のリファレンス部分は自動生成)
.github/workflows/      CI(ビルド+テスト+Doc チェック)/ Release / Docs 公開

    プラグインごとに次のターゲットができます。

    ターゲット 中身
    <Name> 配布用バイナリ(Mac: .plugin、Windows: .dll)→ build/<preset>/plugins/<os>/<KIND>/
    <Name>_host tdmock にプラグインを載せた実行ファイル。--smoke / --describe
    <Name>_tests tests/*.cpp があるときの GoogleTest

    必要なもの¶

    • CMake 3.25+、Xcode Command Line Tools(Mac)/ Visual Studio 2022(Windows)
    • Mac: brew install googletest(無ければ自動でダウンロードします)
    • ドキュメントのプレビュー: python3 tools/site.py serve(依存はハッシュ付きで固定した docs/requirements.lock から自動で入ります)

    日常の流れ¶

    cmake --preset dev                 # 構成(新しいプラグインを追加したときも)
cmake --build --preset dev         # 全プラグイン+テストをビルド
ctest --preset dev                 # 全テスト
python3 tools/gen_docs.py          # パラメータ表を docs に反映

    1 つだけ: ctest --preset dev -R LifeGameCHOP、ビルドも絞るなら cmake --preset dev -DTDP_ONLY=LifeGameCHOP。

    従来の cd CHOP/X && mkdir build && cd build && cmake ../../.. && cmake --build . も動きます (出力は CHOP/X/build/mac/)。

    TouchDesigner で確認¶

    ビルドした .plugin を TouchDesigner の Plugins フォルダにコピーするか、 CPlusPlus CHOP / TOP の Plugin Path に build/dev/plugins/mac/... を指定します。

    自動メンテナンス¶

    プラグインを追加・変更すると、この Mac が自動で次のことを行います(セットアップ不要)。

    何を 内容
    ビルドとテスト(Mac) 全プラグインをビルドし、smoke / unit / portability テストを実行
    ドキュメント docs/plugins/<名前>.md を作成・更新(パラメータ表はプラグイン本体から)
    処理時間 tools/bench.py で計測
    Windows SSH 先の Windows 機でビルド・テスト・計測(つながらないときは飛ばします)
    サンプル <名前>Example.toe を作り、裏で起動した TouchDesigner で開いて、エラーが出ないこと・cook 時間・出力のプレビューを確認
    サイト build/site をローカルに作り直す(公開はリリース時だけ)
    • 実行するのは tools/maintain.py です。LaunchAgent(python3 tools/maintain.py install で登録済み)が 15 分ごと、またはプラグインのフォルダが増えたときに動かします。変更が無ければ何もしません(0.1 秒)。
    • 編集中に動き出さないよう、最後の変更から 60 秒たってから始めます。
    • 対象は変わったプラグインだけです。共通部分(cmake/、testing/、tools/ の一部、TDLib/)が変わったときは全部やり直します。
    • 結果は macOS の通知と build/maintain/report.md に出ます(python3 tools/maintain.py status)。
    • 手動で今すぐ: python3 tools/maintain.py --now、全部やり直し: --all、止める: python3 tools/maintain.py uninstall

    使用例とTouchDesigner テスト(手順で書く)¶

    使用例とTD上のテストは、ネットワークを組む Python の手順 として書きます。 実際の TouchDesigner(裏で起動する確認用)が手順どおりにネットワークを組むので、プラグインのパラメータも既定値以外を指定できます。

    使用例 <plugin>/examples/<名前>.py — ドキュメントの「使用例」と、zip に入る .toe になります。

    """1 色あたり 2 ビット

各チャンネル 4 段階だけになり、ポスターのような強い見た目になります。
"""


def build(ex):
    img = ex.input("moviefileinTOP")      # in0(プラグインの入力に順につながる)
    ex.plugin(img, Bitspercolor=2)        # プラグイン本体。パラメータは自由に指定
    • 最初の行がページ上の見出し、残りが説明文です。out1(既定ではプラグインの出力)の絵がサムネイルになります。
    • ex.op("levelTOP", input=node, opacity=0.5) で後段の処理を足せます。ex.out(node) で out1 につなぐノードを選べます。
    • CHOP を指定するパラメータには ex.source("noiseCHOP", ...) で作った CHOP をそのまま渡します(例: TOP/Instance/InstanceTOP/examples/default.py)。
    • 使用例が 1 つも無いプラグインには、既定の入力と既定のパラメータの使用例が自動で作られます。
    • デバイスにつながるなど、確認用 TD で動かしてはいけないものは RUN_IN_TD = "理由" と書きます(既定値のまま .toe だけ作ります)。

    TD テスト <plugin>/tests/td_<名前>.py — test_ で始まる関数をそれぞれ空のネットワークから実行します。

    def test_two_bits_gives_four_levels(ex):
    src = ex.input("noiseTOP", resolutionw=64, resolutionh=64, type="random", mono=False)
    crushed = ex.plugin(src, Bitspercolor=2)
    ex.cook()
    ex.assert_no_errors()
    levels = {int(round(v * 255)) for v in crushed.numpyArray()[..., :3].ravel()}
    assert levels <= {0, 64, 128, 192}

    node.numpyArray() で TOP の画素や CHOP のサンプルを numpy の配列として取り出せます。 tdmock の単体テストでは確かめられない、TD 上での実際の出力を確認するためのものです。

    仕組み: プラグインごとに確認用 TD を 1 つ開き(プラグインのバイナリと同じフォルダの空のプロジェクト)、 使用例を組んで /project1 を .tox として保存し、テストを実行します。 保存した .tox の中身をきれいな .toe の雛形に入れ(toeexpand / toecollapse)、 できた .toe を別の TD で開き直して、エラー・cook 時間・60 fps への影響を確認します。 プロジェクト全体は保存しないので、ダイアログは出ません。結果は build/examples/results.json。

    python3 tools/td_examples.py                    # 全プラグイン
python3 tools/td_examples.py --only BitCrushTOP

    Mac では OpenMP を使いません

    プラグインごとに別々の libomp が TouchDesigner に読み込まれるとクラッシュするため、Mac 版は #pragma omp を無視してビルドします(cmake/omp_stub/omp.h)。Windows 版は MSVC の OpenMP を使います。

    パレットの公開¶

    パレット(.tox)は TouchDesigner で作って直す のが基本です。いつも通り Palette ブラウザ(My Components)や TDAgent の palette_save で保存すれば、あとは自動で取り込まれます。

    1. 公開するものを選ぶ: palettes/publish.txt に 1 行ずつ書きます(パレットフォルダからの相対パス、* 可)。 
      UV/mandalaUV
AudioSpectrum/*
    2. 自動で行われること(自動メンテナンス、または python3 tools/palettes.py all)
      • TD のパレットフォルダから palettes/<フォルダ>/<名前>.tox にコピー(git で履歴が残り、git diff はテキストで読めます)
      • 確認用 TD で読み込み、help DAT の説明・カスタムパラメータ・入出力・中のオペレータ を調べます
      • 中のオペレータを全部たどって Custom オペレータ(依存プラグイン) を列挙し、このリポジトリのプラグインならそのページにリンク
      • 使用例を作って .toe にし、出力をサムネイルに
      • docs/palettes/ のページと一覧を生成
    3. 公開: python3 tools/palettes.py publish(確認あり)で、公開リポジトリの Palettes/<フォルダ>/ と README の一覧を更新し、サイトも更新します。 TD で問題が見つかったパレットがあると公開しません。

    ページの内容はすべてコンポーネント自体から作るので、説明を直すときは TD で help DAT を編集 します。 help の中の ```spec ブロック(Agent 用の入出力の説明)は、ページでは入出力の表に使われ、本文には出ません。

    使用例の手順: palettes/<フォルダ>/<名前>.example.py(複数なら <名前>.example_2.py など)

    """バナナの万華鏡

バナナの画像に、N=6 の mandalaUV を Remap TOP で当てたものです。
"""


def build(ex, tox):
    img = ex.input("moviefileinTOP")
    uv = ex.palette(tox, None, N=6)               # パレットを読み込み、入力を順につなぐ
    ex.out(ex.op("remapTOP", input=[img, uv]))    # out1 の絵がサムネイル

    手順が無いパレットは、入力の種類に合わせた既定のソース(TOP なら画像、CHOP なら Noise)をつないだ使用例が自動で作られます。 手書きで足したいこと(過去のサンプルへのリンクなど)は palettes/<フォルダ>/<名前>.notes.md に書くとページの最後に入ります。

    依存プラグインの版

    Custom オペレータは、TouchDesigner の Plugins フォルダに入っている版が使われます。確認用 TD でも同じなので、 古い版が入っているとパレットの確認結果もその版のものになります。

    新しいプラグインを作る¶

    python3 tools/new_plugin.py CHOP Gain                    # → CHOP/GainCHOP
python3 tools/new_plugin.py TOP Tint --category Color    # → TOP/Color/TintTOP

    作ったら、あとは何もしなくても上の自動メンテナンスが、テスト・ドキュメント・Windows 版・サンプルの確認まで行います。

    テンプレートは「アルゴリズム(<Name>Core.h、TD 型を使わない)」と 「TD とのつなぎ(<Name>.cpp)」と「パラメータ(<Name>Parameters.*)」に分かれていて、 テストも両方の書き方の例が入っています。opType の重複や命名規則違反はスクリプトが弾きます。

    依存ライブラリがある場合は plugin.cmake を置きます(書ける変数は cmake/TDPlugin.cmake の冒頭を参照)。 例: CHOP/MidiFileInCHOP/plugin.cmake, CHOP/BLEInCHOP/plugin.cmake。

    テスト¶

    自動で全プラグインにかかるもの¶

    テスト 確認内容
    <Name>.smoke apiVersion、opType の命名規則、パラメータ名の規則・重複、clamp と既定値の矛盾、入力を与えて 3 回 cook して落ちない / NaN を出さない、宣言していないパラメータを読んでいない(setup と eval の名前の typo)、TOP のアップロードサイズ
    <Name>.portable (Mac) バイナリが Homebrew など手元にしかない dylib や OpenMP ランタイムに依存していない(Mac では OpenMP を使わずにビルドします。複数のプラグインが別々の libomp を読み込むと TD がクラッシュするため)

    プラグイン固有のテスト¶

    <plugin>/tests/*.cpp に GoogleTest を書きます。tdmock が TouchDesigner の代わりをします。

    #include "tdmock/tdmock.h"
#include <gtest/gtest.h>

TEST(LifeGame, OutputShape) {
  auto h = tdmock::makeCHOP();                     // このテストにリンクされたプラグイン
  h->inputs().set("Width", 17).set("Height", 5);  // パラメータ(既定値から開始)
  h->inputs().setMenu("Edgemode", "Torus");
  auto r = h->cook();                              // TD と同じ順序で呼び出し
  EXPECT_EQ(r.numChannels(), 5);
  EXPECT_EQ(r.numSamples(), 17);
}

TEST(BitCrush, OneBit) {
  auto h = tdmock::makeTOP();
  h->inputs().setInputTOP(0, tdmock::Image::gradient(32, 16));
  h->inputs().set("Bitspercolor", 1);
  const tdmock::Image *out = h->cook().output();   // uploadBuffer された画像
  // out->get(x, y, channel) は 0..1、BGRA でも RGBA 順で読めます
}

    主な API(testing/tdmock/include/tdmock/tdmock.h):

    • inputs().set / setString / setMenu / setInputCHOP / setInputTOP / clearInputs / time()
    • CHOPData::sine(nChans, nSamples)、Image::gradient(w, h)、Image::converted(format)
    • cook() → CHOP: CHOPResult(channel(i or name), data.names, messages.error…)/ TOP: TOPResult(output(index), uploads, problems)
    • params().find(name) で宣言内容(既定値・範囲・メニュー)を確認
    • context().liveBuffers() で TOP のバッファの解放漏れを確認

    tdmock でテストできないもの

    GPU(CUDA / OpenGL)、Python コールバック、DAT/SOP 入力、実デバイス(BLE など)は nullptr を返すだけです。こうした部分はロジックを Core に分けてテストし、 最終確認は TouchDesigner 上で行ってください。

    検証ゲート(自動で入る変更の合否判定)¶

    エージェントによる自動の変更は、すべて tools/gate.py check に合格しなければ取り込まれません。 ルールはリポジトリ直下の CONSTITUTION.md にあり、判定に使うファイルは ~/.tdp/constitution.lock(リポジトリの外)に固定されています。

    # ゲート 不合格になる条件
    0 憲法 判定に使うファイルの変更、既存テストの変更・削除、正解出力の変更、既知の不具合リストの追加、サプライチェーン検査の失敗
    1 テスト ビルド失敗、smoke / unit / portability テストの失敗(毎回クリーンビルド)
    1b Lint clang-tidy(静的解析・バグの出やすい書き方・性能、-Wall -Wextra)と ruff(Python)で、既存分(lint-baseline.json)以外の指摘
    2 出力の比較 正解の出力(<plugin>/oracle/golden-mac.json)と違う。入力は gradient / noise / checker を順に使う
    3 乱数試験 極端なパラメータ・入力で、既知リストに無い種類の失敗(クラッシュ、ハング、NaN など)
    4 サニタイザ ASan / UBSan ビルドでのテストと乱数試験で、メモリ破壊や未定義動作
    4b メモリリーク macOS の leaks で、各プラグインの cook と単体テストのリーク(既存分 leaks-baseline.json を超えたら不合格)
    5 TouchDesigner サンプルが TD で正常に開けない。または TD 上の cook 時間で 60 fps が 2 fps 以上落ちる(すでに落ちているものは fps-known.json に記録され、そこから 15% 以上遅くなると不合格)(--td)
    6 Windows SSH 先でのビルド・テストの失敗(--windows) 
    python3 tools/gate.py check                       # 作業中の変更を判定(HEAD と比較)
python3 tools/gate.py check --track perf          # 速度改善: 出力は完全に同じであること
python3 tools/gate.py check --track bugfix --plugin BitCrushTOP   # そのプラグインだけ出力の変化を許可
python3 tools/oracle.py record --only <名前>       # 正解の出力を記録(新しいプラグインは自動)
python3 tools/oracle.py fuzz                       # 乱数試験だけ

    コミットとマージ¶

    • git commit のたびに .githooks/pre-commit が数秒で、サプライチェーン・憲法・変更したファイルの Lint を確認します。
    • main への取り込みは python3 tools/merge.py <ブランチ> だけです(ローカルのマージリクエスト)。 ブランチを一時的な作業フォルダに取り出し、main 側の固定された判定でゲートを全部通したときだけマージします。 それ以外のマージは pre-merge-commit フックが拒否します。
    git switch -c fix/bitcrush-mono8   # 作業用ブランチ
# ...修正してコミット...
git switch main

    サプライチェーン(外部の依存)¶

    外部から取り込むものはすべて deps.lock.json に、正確なバージョンかコミット・SHA-256・公開日と一緒に記録します。 公開から 7 日たっていないバージョンは取り込みません(乗っ取られたリリースの多くは 1 週間以内に見つかって取り下げられるため)。 一覧とリスクは SUPPLY_CHAIN.md にあります。

    python3 tools/supply_chain.py check                     # コミットのたび・ゲート 0 で自動
python3 tools/supply_chain.py check --online            # 公開元で日付とハッシュを再確認
python3 tools/supply_chain.py add-pypi foo==1.2.3        # 7 日未満なら拒否(--older で 7 日以上前の最新版)
    • GoogleTest は固定した URL とハッシュからだけ取得します(Homebrew の版は使いません)。
    • GitHub Actions はタグではなくコミットで固定しています。
    • ドキュメントのビルドと Lint ツールは pip --require-hashes で、固定したものだけを入れます。
    • CMake・clang-tidy など Homebrew のツールは記録だけして、版が変わると check が知らせます。むやみに brew upgrade しないでください。

    判定の仕組み自体(tools/gate.py、tools/oracle.py、testing/ など)を変えたときは、 内容を確認してから python3 tools/gate.py pin で固定し直します(人が行う操作です)。

    ドキュメント¶

    docs/plugins/<Name>.md のうち <!-- tdp:auto:begin --> 〜 <!-- tdp:auto:end --> の間 (OP 情報とパラメータ表)は tools/gen_docs.py がプラグイン本体から生成します。 その外側(概要・使い方・画像)は自由に書いてください。新規ページは Publish/README.md の説明文があればそれを下書きとして使います。

    • CI は gen_docs.py --check で、コードとドキュメントがずれていると失敗します → python3 tools/gen_docs.py を実行してコミットしてください。
    • サイトのプレビュー: python3 tools/site.py serve(初回は MkDocs を build/.venv-docs に自動インストール)
    • サイトの公開はリリース時に自動で行われます(手動なら python3 tools/site.py deploy)。

    TDAgent に Custom OP を説明させたいときは、~/.tdagent/config.json の custom_docs に docs/plugins/*.md を追加すると、パラメータ表がそのまま使われます。

    Windows でのテスト(SSH)¶

    SSH で入れる Windows 機(既定: SHINH-MPC.local、環境変数 TDP_WINDOWS_HOST で変更)で、 ビルド・全テスト・処理時間の計測・zip 作成までを Mac から実行できます。

    python3 tools/remote.py                       # 全プラグイン
python3 tools/remote.py --only LifeGameCHOP   # 1 つだけ
    • ソースを %USERPROFILE%\tdp-remote\src に送って tools/windows/remote_build.bat を実行します。 ビルドフォルダは残すので 2 回目からは差分ビルドです。
    • 結果は build/remote-windows/(dist/*.zip、bench-windows.json、junit-windows.xml、log.txt)。
    • Windows 側に必要なもの: Visual Studio 2022(C++ と「C++ CMake tools」)、Python(py)、OpenSSH サーバー。

    処理時間の計測¶

    フレームレートへの影響(60 fps が何 fps になるか)¶

    サンプルを TouchDesigner で開いたときに、プラグインの OP を繰り返し cook して 1 回あたりの時間を測ります (GPU との転送を含む実際の TD 上の時間。速い方のバッチを採用するので、測り直しのぶれは 3% 程度)。 それを「フレームに余裕の無い 60 fps のプロジェクトに足したら何 fps になるか」に直します。

    60 fps のとき = 1000 / (16.67 ms + cook 時間)

    2 fps 以上落ちる(cook 時間がおよそ 0.58 ms 以上)と要注意です。サイト・リリースノート・自動メンテナンスの 報告に出ます。検証ゲート 5 は、新しく 2 fps 以上落ちる変更と、すでに落ちているものをさらに 15% 以上遅くする変更を止めます。

    実際の fps を直接測らない理由

    裏で起動した TouchDesigner は macOS に省電力のため間引かれるので、生の fps は 20〜60 の間でぶれて使えません。 cook 時間は同期して測るので、この影響を受けません。

    python3 tools/bench.py                          # 全プラグイン(Release ビルド)
python3 tools/bench.py --only BitCrushTOP

    各プラグインを tdmock 上で同じ入力のまま何十回も cook し、1 回あたりの中央値を出します。 既定の入力は smoke テストと同じ(TOP は 1280x720)。条件を変えたいときは <plugin>/bench.json に書きます (書き方は tools/bench.py の先頭。例: TOP/Glitches/BitCrushTOP/bench.json、CHOP/DotCHOP/bench.json)。 計測結果はサイトの各プラグインのページ・「処理時間」ページ・リリースノートに載ります。

    数字の意味

    TouchDesigner の外で CPU 処理だけを計った値です(GPU とのやり取りは含みません)。 版や設定ごとの比較、Mac / Windows の差を見る目安として使ってください。

    リリース¶

    リリースは Mac から tools/release.py で行います。トークンも GitHub Actions も不要で、 この Mac の gh のログイン(gh auth status)を使って公開リポジトリ TouchDesignerShareDatas に Release を作ります。

    python3 tools/release.py LifeGameCHOP 1.2.0 --dry-run   # まず確認(公開しない)
python3 tools/release.py LifeGameCHOP 1.2.0             # 1 プラグインだけ → タグ LifeGameCHOP-v1.2.0
python3 tools/release.py all 1.2.0                      # 全部 → タグ v1.2.0

    やること: Mac でビルド+全テスト+ドキュメントの同期確認 → Windows で同じこと(SSH)→ 両方で処理時間を計測 → zip とリリースノートを build/release-dist/<tag>/ に作成 → 確認のあと Release を作成 → サイトを更新。

    タグ Release 添付される zip
    v1.2.0 TouchDesigner Plugins 1.2.0(Latest) 全プラグインそれぞれの <Plugin>-1.2.0-<os>.zip + まとめ TDPlugins-1.2.0-<os>.zip
    LifeGameCHOP-v1.2.0 Life Game 1.2.0 LifeGameCHOP-1.2.0-mac.zip / -windows.zip だけ
    • リリースノートは docs/plugins/<Plugin>.md(概要+パラメータ表+処理時間+導入方法)から作られます。 先にドキュメントの概要を書いておくとそのまま説明になります。
    • 1 プラグインのリリースは "Latest" にならないので、まとめリリースの Latest 表示は崩れません。
    • 各 zip には説明の README.md が同梱されます。

    サイト¶

    サイト(https://shinh0707.github.io/TouchDesignerShareDatas/)のダウンロードボタンは、閲覧時にブラウザが 公開リポジトリの Release 一覧を読み、そのプラグインを含む最新のリリースを表示します。リリース後にサイトを作り直す必要はありません。

    TD の majorVersion / minorVersion(OP の情報に出るバージョン)はタグとは別なので、 互換性が変わるときは Fill*PluginInfo の値も上げてください。

    CI(任意)¶

    ソースを GitHub に置いた場合は .github/workflows/ci.yml が push / PR ごとに Mac と Windows で ビルド・テスト・ドキュメントの同期チェックを行います(トークン不要)。リリースは上の tools/release.py で行います。

    Windows 版について

    以前 Publish/Plugins/ に置いていたバイナリは削除済みです(Windows 用 DLL が実は Mac 用で動かなかったため)。配布は Releases のみです。 tools/remote.py / tools/release.py が作る .dll が本物の Windows 版です。 BLEInCHOP は SimpleBLE が無い Windows ではスキップされます。
